# Kokoro deployment

The worker publishes no ports. It supports two deployment modes: a persistent Docker host (`python worker.py`) or a scheduled container job (`python worker.py --once`). In `--once` mode it claims at most one queued audio job, exits successfully when the queue is empty, and exits with an error after recording a failed job. It only loads Kokoro after a job is claimed.

## Recommended when no always-on host exists

For a strictly zero additional cloud spend target, the public GitHub repository can run the standard hosted runner with `.github/workflows/ai-factory-audio.yml`. It starts at 16:17 Asia/Ho_Chi_Minh each day or manually via Actions, claims at most one queued audio job, and exits. The text workflow creates Listening at 15:37, Reading at 15:47, Writing at 15:57 and Speaking at 16:07 local time. These UTC cron times fall after both the app's 00:00 UTC job-count reset (07:00 local) and Gemini's midnight Pacific daily-quota reset (14:00 or 15:00 local, depending on daylight saving time). GitHub may delay or occasionally drop scheduled runs; check the Actions history rather than assuming an exact execution minute. The workflow has no artifact upload or paid runner. Add repository Actions secrets `AI_FACTORY_SUPABASE_URL` and `AI_FACTORY_SERVICE_ROLE_KEY`; without both, the workflow skips safely. The service-role key grants broad Supabase access, so restrict write access to the repository and do not expose the secrets in logs, PR workflows or client code. A passing workflow proves audio processing, but it does not create new questions by itself. Keep `max_concurrency=1` in `ai_factory_settings`.

GitHub's standard runner is [free for public repositories](https://docs.github.com/en/actions/concepts/billing-and-usage). This covers runner time, not existing Supabase or other product quotas. The separate Google AI Studio project is unbilled and uses [Gemini 3.5 Flash-Lite's Free tier](https://ai.google.dev/gemini-api/docs/pricing); model requests stop at its free limit. The audio workflow processes only jobs already in the queue. Text generation is controlled separately by the confirmed Free-tier key and production settings.

If a paid deployment is later acceptable, use a Cloud Run Job with one task, one concurrent execution, a 60-minute task timeout and zero platform retries. Trigger it from Cloud Scheduler at a low frequency while production volume is small. The database lease and attempt limit handle a worker that exits unexpectedly; a later scheduled run can reclaim that job after the 15-minute lease expires. Use Secret Manager for `SUPABASE_SERVICE_ROLE_KEY`; set `SUPABASE_URL` as a normal environment variable. The container command is `python worker.py --once`. Start with a manual job execution and measure actual runtime, peak memory, image pull time, model download time and cost before enabling the schedule. Cloud Run's ephemeral filesystem does not preserve the current WAV/model cache between executions; pre-bake verified model artifacts into the image or add a persistent cache before scheduling frequent runs. ASR also downloads its model on a fresh container. Configure billing alerts because compute, image storage, downloads and Secret Manager can incur charges.

Cloud Run Jobs can be [run on a schedule](https://cloud.google.com/run/docs/execute/jobs-on-schedule); see its [job settings](https://cloud.google.com/run/docs/create-jobs), [secret configuration](https://cloud.google.com/run/docs/configuring/jobs/secrets) and [pricing](https://cloud.google.com/run/pricing). This deployment has **not** been provisioned: it needs a Google Cloud project with billing and permission to create jobs, Scheduler triggers, images and secrets. The production generation switch remains off until the job is tested and content review is ready.

## Persistent Docker host

Use a CPU or GPU host with Docker, outbound access to Supabase and enough storage for the model plus cached WAVs. Do not run the model in Vercel.

1. Apply `supabase/migrations/202610270010_ai_content_factory.sql` to the target project and inspect the new tables, policies, RPC and storage bucket.
2. Set `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` on the Next server. Copy `services/audio-worker/.env.example` to `services/audio-worker/.env` on the worker host and fill the same project URL plus its service-role key. Keep the file outside Git and restrict file access. The key must never reach client code.
3. In `services/audio-worker`, run `docker compose build` then `docker compose up -d`. The first inference downloads the verified Kokoro 1.0 weights. Mount the cache volume persistently.
4. In Admin, create one pilot. Watch worker logs and the queue until `awaiting_review`. Listen to the complete draft, verify all answers, then approve the audio. In the IELTS bank, inspect the revised exam, mark ready and publish. Complete a student attempt and confirm scoring and saved progress in staging.

If Docker is unavailable, use Python 3.11 or 3.12, install `requirements.txt`, `python -m spacy download en_core_web_sm`, and `espeak-ng`, set `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and `AUDIO_CACHE_DIR`, then run `python worker.py`. Kokoro's package declares Python `<3.14`; Python 3.14 is not supported for this worker.

Rollback: stop the worker; disable production scheduling; cancel queued jobs; archive any published factory exam through the bank; retain versioned attempts. Do not drop factory tables or remove storage objects until their references and audit records have been exported. Revert the web deployment separately. Never delete learner attempts during rollback.
